# 埋点与分析数据规范

## Purpose

避免事件、公共属性和用户属性混用，以及统计口径、触发时机、重复回调和恢复流程导致的数据失真。变更与交付执行 [项目变更工作流](project-change-workflow.md)；持久化采用项目现有入口，使用生成式 ES3 链路时另读 [状态持久化](statusutil-es3-persistence.md)。

## Applies When

- 新增、修改或审查 Unity 项目的业务分析事件、事件参数、公共属性及用户属性。
- 处理累计计数、来源归因、异步结果、重试去重、存档恢复或分析 SDK 上报验证。
- 对齐需求表、实现、数据示例及下游统计口径。

## Does Not Apply When

仅修改与业务分析无关的调试日志、性能采样或崩溃堆栈时，不自动执行本规范。服务端权威统计仍需明确数据契约与验证边界，但不要求客户端复制累计器、存档或去重数据库。

## Decision Process

1. 确认数据消费者、现有契约及权威来源，区分新增字段、语义修正和兼容性变更。
2. 为受影响字段确定名称、类型、枚举、单位、统计对象、触发时机、累计范围、重置条件和未知值处理；未确定项显式记录，不用猜测值补齐。
3. 沿真实调用链核对请求、成功发放、实际消耗、业务完成和失败回调，选择契约要求的统计位置。
4. 检查重复回调、重试、重新进入和恢复路径，再按可用环境逐层验证并同步示例。

## MUST

- 明确三类数据的职责：事件参数描述该次行为，公共属性描述事件发生时约定的上下文快照，用户属性描述用户当前状态或长期累计。不能用其中一种已存在代替另一种的接入与验证；公共属性需确认实际取值时刻，避免延迟发送时读到后续状态。
- 修改前明确受影响统计的口径与类型；单次、单局、跨重试累计和用户累计不能互相替代。时间字段必须确认单位及暂停、后台、恢复是否计入；需保留的累计值与重置边界必须在新建、重开、续接和持久化恢复路径一致。
- 成功类统计必须以实际业务成功为依据。点击、广告完成、动画完成或发起扣款不能自动视为发放、消耗或恢复成功；如果契约统计的是请求或尝试，应按该语义单独实现。
- 每项统计必须有明确的权威更新位置，并核对重复调用与重试的影响。同一操作不能因库存层、界面层和上报层重复累计；需要去重时复用项目已有操作身份或状态边界。客户端防重不能被表述为网络端到端恰好一次送达。
- 枚举、来源和数量必须取自真实业务结果，覆盖本次涉及的入口及成功/失败分支。当前库存、累计获得和累计使用分别验证；总量不能冒充分类计数，也不能凭总量推算无法还原的历史分类。
- 新增累计字段必须明确旧用户的初值、统计起点和迁移行为；无法恢复的历史数据不能声称完整。改名、改类型、删除或拆分字段必须检查现有消费者，并记录兼容策略或明确的同步切换约定。
- 验证结论必须区分本地构造、SDK 调用或入队、目标平台发送和后台接收。仅有编辑器日志、模拟 SDK 或编译结果时，不得宣称真实上报链路已通过。

## SHOULD

- 复用现有分析入口与业务计数入口，避免界面自行拼装同义字段或维护另一套累计值。
- 从行为来源向下传递归因信息，避免在公共中间层为所有入口硬编码同一个来源。
- 用少量代表性数据示例对齐字段集合、类型、合法枚举和累计口径；示例区分真实值、占位值及尚未实现项。
- 修改后同步受影响的契约、示例和已知下游配置；公共字段复用同一取值规则，同时保留各事件自身的必要差异。

## CONSIDER

- 多端、离线重放或服务端权威场景可使用版本化契约、操作标识或服务端幂等，按实际投递保证决定，不为简单本地场景引入额外系统。
- SDK 存在类型、字段名、长度或保留字限制时，在现有适配层统一处理，并验证转换没有改变统计含义。

## AVOID

- 为匹配表格编造关卡类型、实验分组、来源或成功结果。
- 只新增上报字段而遗漏计数、清零、保存或恢复路径。
- 把静态示例、调试输出或调用成功当作后台已收到的证据。
- 为本次新增字段无依据地重写整个分析系统或批量迁移无关历史数据。

## Exceptions

统计权威可以位于客户端、服务端或分析平台；只修改本次职责范围内的链路。SDK 不支持动态公共属性时，可在事件构造时生成约定快照；不要求更换 SDK。项目明确采用近似统计、采样或允许重复时，记录其语义与误差边界，按该契约验收，不额外承诺精确累计。

## Validation

- [ ] 受影响字段的类别、类型、枚举、单位、累计范围、重置条件及未知值行为已核对。
- [ ] 请求、成功、失败、取消和重复回调符合各自契约，实际业务结果与上报值一致。
- [ ] 所涉及的来源和类别入口已覆盖，未把库存或总量误当分类累计。
- [ ] 涉及重开、续接或累计持久化时，清零与恢复结果一致，旧数据的统计起点明确。
- [ ] 破坏性字段变更及对应消费者已有兼容安排，文档与示例反映最终实现。
- [ ] 已报告实际验证的平台与层级，无法执行的发送或后台接收验证明确列出。

## Validation Cases

- 正向：一次实际成功消耗更新本局和用户累计，再构造事件；连续执行两次，分别核对单次事件、当前库存和两种累计，不在上报入口再次加计数。
- 反向：请求已发出但业务失败或取消，成功消耗不增加；重复成功回调不重复增加同一项统计。仅修改调试日志时不引入用户属性或分析存档。
- 边界：旧存档缺少新增分类计数，明确从启用时累计或使用可证明的迁移来源；不把默认零解释为用户历史从未使用。离线重放时区分原始事件快照与发送时状态。
- 架构边界：服务端已负责权威累计和去重时，客户端按契约传递操作及结果，不再创建第二套权威累计器；此案例用于适用性推演，不代表已完成真实服务端集成测试。
