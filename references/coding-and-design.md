# 基础编码与设计规范

## Purpose

让 Unity 代码易读、易维护、易测试，职责、依赖和数据流可追踪；以可读性和简单实现为先，避免为了套设计模式增加抽象。

## Applies When

- 新增、重构、修复或审查第一方 C# 代码，包括运行时和 Editor 工具。
- 设计组件职责、业务接口、依赖传递、配置、命名或注释。

## Does Not Apply When

- 仅修改美术或说明文档，不要求顺带改写代码。
- 第三方、生成文件和历史代码不因本规范引入而统一重构；修改边界按 [项目变更工作流](project-change-workflow.md) 和 [资源与生成文件规范](assets-and-generated-files.md) 判断。
- 非 MonoBehaviour 架构沿用自己的调度和依赖模型，不强行改成组件、接口注入或 ScriptableObject。

## Decision Process

1. 阅读项目约束和相邻实现，确认入口、职责、依赖、调用者与现有命名。
2. 选择最简单且符合既有架构的方案；确认能否扩展现有能力，避免继续堆叠无关分支。
3. 按下列设计原则检查职责边界，不为单次使用创建无收益的接口或框架。
4. 标记高频入口及其调用链；涉及运行时代码时同时阅读 [运行时性能与生命周期](runtime-performance-and-lifetime.md)。
5. 检查必要注释、序列化兼容和对应验证范围，再执行变更。

## Design Principles

以下原则默认按 SHOULD 应用，以实际职责和变化风险判断拆分，不按类数量或模式数量验收：

| 原则 | 可观察的检查方式 |
| --- | --- |
| 单一职责 | 类有明确变化原因；输入、状态、表现、数据处理和存储各有责任边界，不把无关功能持续塞进同一个 Manager |
| 开闭原则 | 重复出现的可变行为优先通过组合、策略或现有扩展点表达；固定且清晰的分支可以保留，不为消灭所有 switch 建框架 |
| 里氏替换 | 子类保持父类的调用契约、结果语义和状态约束；无法安全替换时改用组合或明确不同接口 |
| 接口隔离 | 接口按调用者需要保持小而专一，不强迫实现无用成员 |
| 依赖倒置 | 高层逻辑不以场景搜索隐式获取低层依赖；在有替换、测试或隔离价值处使用抽象 |
| 组合优于继承 | 默认通过组件、辅助类、服务或策略复用能力；继承关系稳定且确实更简单时可以继承，避免深层继承树 |

## MUST

- 修改公共接口或继承行为时，必须检查已知调用者和既有契约，不能引入未声明的副作用或让合法调用失效。
- 关键流程、复杂算法、状态转换、跨边界计算、缓存策略和生命周期处理必须有简洁且同步维护的注释，说明职责、原因、约束或性能风险。简单直观的方法不强制套模板。
- 修改序列化字段的名称、类型或访问方式时，必须检查已有资源引用和数据兼容；不能仅为统一命名破坏 Inspector 配置。资源处理复用 [资源与生成文件规范](assets-and-generated-files.md)。

## SHOULD

- `MonoBehaviour` 应主要承担 Unity 生命周期、场景引用和流程协调；可独立的业务逻辑与算法尽量放入普通 C# 类。
- `Awake`、`Start`、`Update`、`LateUpdate`、`FixedUpdate` 应简短清晰；方法混合分支、状态切换、数学计算和视图刷新时，按职责拆分，而非仅按行数拆分。
- `Update` 用于逐帧逻辑，`FixedUpdate` 用于需要物理步进的逻辑，`LateUpdate` 用于相机跟随和最终姿态修正；具体顺序与项目调度一致。
- 依赖优先经序列化引用、显式初始化、组合根或项目现有注入机制传递；不要把场景查找当作通用依赖注入。
- 可调参数放入现有配置、ScriptableObject 或集中常量，避免业务代码散落魔法数字；序列化字段通过名称、Header 或 Tooltip 表达策划、美术可理解的用途。
- 管理器、服务职责应单一，数据流显式；工具类仅保留无状态辅助方法。已有可靠框架和受控的全局服务不因形式统一被替换。

## Naming

以下为 SHOULD 默认值；项目已有约定优先，避免局部引入第二套风格：

- 类型、方法、属性和公有成员：`PascalCase`。
- 私有字段：优先项目既有风格；无约定时使用 `_camelCase`。
- 参数和局部变量：`camelCase`。
- 布尔值表达清晰判断，如 `isDragging`、`hasTarget`、`canRotate`；前缀随字段风格和可见性调整。

## Comments

复杂方法和关键入口优先使用下面的说明结构，按实际内容省略无关项，不填空话：

```csharp
/// <summary>
/// 作用：说明职责及调用方可依赖的结果。
/// 关键流程：说明不直观的调用链、状态转换或边界处理。
/// 性能注意点：说明缓存、复用、分配限制及其原因。
/// </summary>
```

短代码块优先解释原因和约束，同一文件保持风格一致：

```csharp
// 作用：说明这段处理为什么存在。
// 注意：说明边界条件、状态约束或性能原因。
```

## AVOID

- 避免巨型 Manager、无边界的静态可变全局状态，以及 UI、输入、存档、玩法混为一体。
- 避免深层继承、万能接口、无实际替换需求的抽象和为统一风格替换可靠方案。
- 避免重复代码字面意思的逐行注释，或保留与当前实现不一致的旧注释。

## Exceptions

- SHOULD 的偏离需要说明项目依据；设计原则不要求所有类都实现接口或全部业务脱离 MonoBehaviour。
- MUST 的覆盖遵循 [Skill 优先级](../SKILL.md#precedence)。有意偏离时记录原因、性能和维护代价及验证结论，不能静默放宽项目要求。
- 项目可保留更严格规则和局部例外；共享库不收录项目专属路径、业务类名或一次性参数。

## Validation

- [ ] 方案符合项目边界和上述设计原则，抽象数量与实际变化需求匹配。
- [ ] 已检查扩展方式、依赖传递、方法职责及隐式耦合或副作用。
- [ ] 已识别运行时热路径，并检查缓存、分配、所有权和更简单的生命周期方案。
- [ ] 命名遵循现有风格，序列化和公共契约未被意外破坏。
- [ ] 主要代码职责清晰，关键代码注释说明原因、流程或约束，且与实现同步。
- [ ] 已执行 [项目变更工作流](project-change-workflow.md) 中与风险匹配的验证；有意偏离有记录。

## Validation Cases

- 正向：给既有玩法新增一种可替换行为，先检查现有扩展点，隔离变化职责并明确依赖，关键状态转换补充注释。
- 反向：修复只有一次调用的简单计算，不为满足 SOLID 新建服务层，不因私有字段默认前缀重命名已有序列化字段。
- 边界：项目使用 ECS 或现有框架管理依赖，保留其系统调度和注入方式；普通 C# 算法仍检查职责和调用契约，不强制引入 MonoBehaviour。

## Project Questions

- 哪些代码属于第一方、第三方或生成结果？项目既有命名和架构边界是什么？
- 哪些依赖需要替换或隔离测试，哪些生命周期由现有框架管理？
- 是否有依赖字段名的序列化数据、反射、生成绑定或公共调用者？
