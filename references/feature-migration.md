# 跨项目功能迁移规范

## Purpose

在 Unity 项目之间迁移完整功能行为，而不是只复制能够编译的脚本。保持资源、Prefab、配置、状态、生命周期、生成链路和验证范围完整，同时尊重目标项目架构。

## Applies When

- 从一个 Unity 项目复制、移植、重建或同步功能到另一个项目。
- 两个项目存在相似功能，但框架、资源系统、UI、状态或服务 API 不同。
- 迁移涉及脚本、Prefab、资源、配置、语言、音效、埋点或生成工具。

## Migration Classes

迁移前把内容分为：

- 一致迁移：目标项目应保持相同结构和行为。
- 目标适配：保留功能语义，替换为目标项目现有基础设施。
- 明确不迁：不属于当前范围，并记录原因。
- 待验证：静态证据不足，必须在 Unity 或目标设备确认。

## Decision Process

1. 还原源功能原型：入口、状态、数据、完整流程、异常路径和验收结果。
2. 记录源项目与目标项目的版本、分支、工作区状态和允许修改范围。
3. 建立脚本、Prefab、资源、配置、语言、声音、埋点和生成工具清单。
4. 比较两边同一职责，而不只比较同名文件。
5. 为每项内容选择迁移类别，并在适配前说明差异和影响。
6. 按依赖顺序迁移并使用目标项目既有基础设施。
7. 分层验证静态引用、编译、Unity 导入、运行时和回归。
8. 清理临时兼容、Fallback、调试内容和无关生成差异。

## MUST

- 必须先还原源功能的用户入口、系统入口、初始化、成功、失败、关闭、重进和异常中断流程。
- 必须追踪关键数据的来源、默认值、读取、写入、刷新、清理和同步规则。
- 必须同时迁移或适配代码、Prefab、资源、`.meta`、配置、本地化、音效、埋点和生成链路中的相关部分。
- 目标项目已有同名文件、资源或功能时必须先比较，不直接覆盖。
- 必须保持目标项目已有的架构、生命周期、资源加载、UI、状态和服务约束。
- 无法直接对齐而需要修改公共框架、扩大 API 或建立兼容层时，必须先说明原因、影响和可选路径。
- 静态分析无法确认的行为必须标记为待验证，不用猜测补全。
- 必须保护两个工作区中已有的未提交改动。
- 编译通过不能作为迁移完成依据；必须验证 Prefab、资源导入、实际加载、核心流程和回归范围。

## SHOULD

- 应该形成简短的功能原型文档，包括入口矩阵、状态数据、资源依赖、外部系统、异常路径和验收场景。
- 应该保持源项目的功能结构和行为，只有基础设施差异才进行目标适配。
- 稳定存在于源 Prefab 的 UI 应该在目标 Prefab 中保持稳定结构；不要为了方便改成运行时创建。
- 应该按依赖闭包迁移资源，并让 Unity Editor 保存复杂 Prefab 和 Scene。
- 应该使用目标项目已有组件、生成器和资源标识，不引入第二套平行机制。
- 应该记录所有保留的目标适配、未迁能力和后续风险。

## CONSIDER

- 目标项目缺少完整基础设施时，考虑在功能边界内建立最小兼容层，并明确退出计划。
- 源实现明显依赖项目偶然结构时，考虑保留行为而适配结构，但需要先获得需求方选择。
- 迁移范围很大时，考虑按可独立验收的用户流程拆分，而不是按文件类型批量复制。

## AVOID

- 避免只搜索产品名或主 Manager 就停止；从入口、状态、资源、事件、配置和销毁路径交叉确认。
- 避免只复制脚本而漏掉 Prefab、`.meta`、资源索引、配置和生成工具。
- 避免为了快速运行修改目标项目底层加载器或公共框架来掩盖缺失依赖。
- 避免把 Editor 专用 Fallback、手工生成文件或临时 Partial 类型作为长期方案。
- 避免只验证首次进入的主路径，忽略关闭、重进、失败、结算、重置和升级迁移。

## Validation Layers

1. 静态引用：脚本纳入编译，GUID、fileID、序列化字段和资源依赖闭合。
2. 编译：Runtime 与 Editor 相关程序集没有新增错误。
3. Unity 导入：Prefab、Scene、材质、Shader、图集和生成文件无新增错误。
4. 运行时：入口、主流程、失败、关闭、重进、数据写入和资源加载正确。
5. 回归：目标项目原有调用者、共享资源、公共 API 和关键流程未被破坏。

## Validation

- [ ] 已形成源功能原型并列出待验证内容。
- [ ] 已记录两个项目基线和允许修改范围。
- [ ] 所有内容已分类为一致迁移、目标适配、明确不迁或待验证。
- [ ] 脚本、Prefab、资源、配置、语言和生成链路清单完整。
- [ ] 同名内容已经比较，没有直接覆盖目标项目差异。
- [ ] 所有目标适配都能说明原因和影响。
- [ ] 资源与 `.meta`、GUID、Prefab 绑定和动态加载已经验证。
- [ ] 初始化、成功、失败、关闭、重进和异常流程已经验证。
- [ ] 临时兼容、Fallback、调试内容和无关生成差异已经清理。
- [ ] 保留的适配、未迁内容和残余风险已经记录。

## Project Questions

- 源功能真正的用户价值、入口和完成标准是什么？
- 两个项目的 Unity 版本、UI、资源、状态、异步和服务框架有何差异？
- 哪些内容必须完全一致，哪些允许目标适配？
- 哪些运行、打包和目标设备场景才能证明迁移完成？
