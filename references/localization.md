# 本地化规范

## Purpose

确保玩家可见文本来自统一数据源，能够安全生成、格式化、回退和动态刷新，并适应不同语言长度、复数规则与文字方向。

## Applies When

- 新增或修改 UI 文本、Toast、按钮、标题、活动说明和格式化文案。
- 修改语言 Key、翻译表、生成枚举、语言资源或语言切换流程。
- 修复缺失翻译、占位符错误、文本溢出、Fallback 或 RTL 问题。

## Decision Process

1. 查找现有语义相同的 Key，优先复用。
2. 找到项目的本地化源数据、生成器、运行时资源和访问 API。
3. 在源数据中新增或修改内容，再运行项目生成流程。
4. 在 UI 中使用稳定 Key 和参数，不拼接依赖语序的句子。
5. 验证默认语言、目标语言、缺失翻译、长文本和动态切换。

## MUST

- 玩家可见文本必须进入项目本地化体系；日志、内部调试和明确不展示给玩家的内容除外。
- 项目存在翻译源和生成器时，必须修改源数据并重新生成，不直接手改生成 Key、枚举或运行时语言文件。
- 格式化文案的占位符必须在所有语言中保持语义一致，并在运行时验证参数数量和顺序。
- 必须定义缺失、空值和未知语言的 Fallback；Fallback 不能导致空界面或核心流程中断。
- 修改语言数据后必须确认 Key 映射、目标语言资源和生成结果一致。
- 语言可在运行时切换时，必须明确已打开界面的刷新机制。

## SHOULD

- Key 应该表达业务位置和文本用途，不直接复制当前某种语言的文案作为永久标识。
- 同义通用文案应该复用公共 Key，避免按页面重复创建。
- 应该使用整句模板和占位符，避免把多个片段拼接成依赖特定语序的句子。
- 应该至少补齐默认或兜底语言，并在提测前确认目标市场语言完整度。
- 应该验证长文本、字号缩放、换行、截断、复数、数字和日期格式。
- 支持 RTL 语言时，应该验证文字方向、对齐、图标顺序和布局镜像。

## CONSIDER

- 有序或成组文案可以使用稳定数字后缀，但不要让 Key 与容易变化的界面层级强耦合。
- 富文本、性别、复数和语言特定语法优先使用项目本地化系统的正式能力，不用业务代码堆条件分支。
- 文案只在单个平台或地区出现时，在数据和条件层表达适用范围，不复制整套 UI。

## AVOID

- 避免在业务逻辑和 Prefab 中新增硬编码玩家文案。
- 避免直接修改自动生成语言文件、Key 类或枚举。
- 避免用真实换行破坏按行索引的语言格式；遵循项目约定的转义和生成方式。
- 避免假设英文宽度能够代表所有语言。

## Line-Indexed Formats

只有项目采用按物理行号索引的语言模板时，才执行以下检查；其他格式遵循其自身数据契约：

- Key map 与所有语言文件的物理行数和 Key 顺序必须一致，生成枚举值与行号映射相符。
- 不插入意外空行，不让一条文案的真实换行占用多条记录；按生成器支持的转义方式保存换行。
- 缺少翻译可以使用已定义的 Fallback，但不能省略对应记录导致后续 Key 错位。

## Validation Cases

- 正向：新增一条按行索引的文案，经源表生成后核对所有语言行数、顺序和枚举映射。
- 反向：JSON 或其他非行号索引方案不要求各文件物理行数一致，也不改成行号格式。
- 边界：翻译含换行或缺失值，按当前生成器契约转义/占位，再验证 Fallback 和相邻 Key 不错位。

## Validation

- [ ] 已搜索并复用现有语义相同的 Key。
- [ ] 已修改正确源数据并运行生成器。
- [ ] 生成 Key、运行时语言资源和使用方一致。
- [ ] 默认语言、目标语言和 Fallback 均能显示。
- [ ] 占位符、复数、数字和日期格式正确。
- [ ] 长文本、换行、缩放和必要的 RTL 布局正确。
- [ ] 动态切换语言后已打开界面能够刷新。
- [ ] 没有新增硬编码玩家文案或手改生成结果。

## Project Questions

- 本地化的唯一源数据、生成器和运行时资源分别在哪里？
- 默认语言和 Fallback 规则是什么？
- 支持哪些语言、复数规则和 RTL 市场？
- UI 在语言切换后如何刷新？
