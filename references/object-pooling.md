# 对象池规范

## Purpose

在确有复用收益的场景降低运行时实例化、销毁和垃圾回收造成的波动，同时控制常驻内存、状态泄漏和生命周期复杂度。

对象池是一种生命周期与所有权管理手段，不是默认性能优化，也不是所有高频对象的必选架构。

## Applies When

至少满足以下大部分条件时考虑对象池：

- 同类对象在可感知时间窗口内频繁创建和销毁。
- 实例化、初始化、销毁或垃圾回收成本已经通过测量确认，或属于目标平台上已知的高风险热点。
- 对象会重复出现，活跃数量存在可估计的常态值和峰值。
- 对象状态能够完整、可靠且可验证地重置。
- 复用对象的常驻内存成本低于运行时抖动带来的风险。

常见候选包括投射物、重复敌人、伤害数字、短生命周期特效、可重复生成的世界对象和高频列表元素。

## Does Not Apply When

以下情况通常不应优先使用对象池：

- 对象只创建少数几次，且没有可测量的性能问题。
- 对象生命周期很长，创建和销毁不在关键路径。
- 对象状态复杂，可靠重置的成本高于重新创建。
- 对象持有大量纹理、网格、音频或其他资源，池化会造成不可接受的常驻内存。
- 对象种类很多但单类复用率很低，池命中率预计很差。
- 现有系统已经由场景、流式加载或资源系统可靠管理生命周期。

## Decision Process

1. 明确要解决的问题：帧时间尖峰、GC、加载延迟，还是重复初始化成本。
2. 记录对象创建频率、同时活跃数量、峰值、实例化成本和资源占用。
3. 判断对象能否定义完整的获取与归还契约。
4. 比较池化复杂度、常驻内存和预计收益。
5. 先在代表性设备和真实负载下验证，再扩大使用范围。

若缺少测量条件，可以把对象池作为待验证假设，但不要把收益描述为既定事实。

## MUST

### Ownership

- 必须定义池的所有者、作用域和销毁时机，例如场景级、玩法会话级或应用级。
- 必须保证一个活跃实例在任意时刻只属于一个池，并且只能被成功归还一次。
- 必须明确谁可以获取、归还、清空和销毁池；不要让任意调用方绕过生命周期契约。
- 必须处理对象被外部提前销毁、场景卸载或池先于对象销毁的情况，避免保留失效引用。

### Acquire And Release Contract

- 必须分别定义创建一次、每次获取、每次归还和最终销毁四个阶段的职责。
- 每次获取时必须建立本次使用所需的完整初始状态，不能依赖上一次归还“碰巧清理干净”。
- 每次归还时必须停止或取消仍会继续运行的行为，包括协程、延迟调用、计时器、Tween、异步操作和回调。
- 每次归还时必须解除仅属于本次使用周期的事件订阅、观察关系和外部注册。
- 必须重置会影响下次使用的 Transform、物理、导航、动画、渲染、音频和玩法状态；只重置实际存在的状态，不要用通用重置掩盖职责不清。
- 必须防止已经归还的对象继续接收输入、碰撞、网络消息或业务事件。
- 异步工作、Tween、协程或完成回调可能晚于归还发生时，必须使用取消、代次标识或等价租约身份，阻止旧工作操作已经复用的实例。
- 完成回调必须具备幂等保护；正常结束、主动中断和场景清理同时发生时，只允许一个路径完成归还。

### Capacity And Failure

- 必须定义池为空时的策略：扩容、拒绝、降级或复用最旧实例。
- 必须定义超过保留容量时的策略：销毁多余实例、暂存或调整容量。
- 必须为获取失败提供可诊断结果；不要通过空引用或随机缺失表现失败。
- 必须避免无上限预热和无上限增长，除非项目明确证明内存与负载边界可控。

### Resource Lifetime

- 必须区分“对象暂时归还”和“对象最终移出池”。只有最终移出时才释放属于实例本身的长期资源。
- 使用 Addressables 或其他带引用计数的资源系统时，必须让实例释放与资源引用释放遵循同一所有权模型，避免提前释放或永久占用。
- 跨场景保留池时，必须确认池中对象及其依赖资源不会引用已经卸载的场景对象。
- 短生命周期池对象触发独立表现时，必须由生命周期足够长的表现控制者管理等待和清理，不能让即将归还的对象继续负责异步完成。
- 在共享容器中清理池对象时，必须只清理当前功能拥有的实例，不能无差别清空其他系统的对象。

## SHOULD

- 应该根据常态并发量设置基础容量，根据可接受的峰值设置最大容量。
- 应该只预热能够改善已知关键路径的数量，避免用最大理论峰值作为默认预热量。
- 应该在开发或测试环境检测重复归还、错误池归还、活跃对象泄漏和失效引用。
- 应该让池化对象拥有清晰的生命周期入口，避免由多个组件分别猜测何时重置。
- 应该保留必要的诊断指标，例如创建总数、获取次数、命中率、扩容次数、峰值活跃数和峰值空闲数。
- 应该让场景级对象池随场景或玩法会话清理，除非跨场景复用有明确收益和所有权设计。
- 应该在低内存平台考虑收缩、容量调整或场景切换时释放空闲对象。

## CONSIDER

- 对象数量稳定且实例化成本集中在加载阶段时，考虑一次性预热。
- 峰值极短但内存昂贵时，考虑允许临时扩容并在负载下降后逐步收缩。
- 多种对象共享生命周期但状态差异很大时，考虑按类型分池，而不是建立过度通用的统一池。
- UI 列表优先考虑虚拟化；只有元素复用确实由对象池解决时，才把对象池作为核心设计。
- 网络对象、权威状态对象或预测对象需要先遵循网络框架的生成与回收模型，再决定是否增加项目级对象池。

## AVOID

- 避免因为“Instantiate/Destroy 很慢”这一泛化说法而池化所有对象。
- 避免把 `OnEnable` 和 `OnDisable` 默认当作完整的获取与归还契约；它们可能因编辑器、父节点或其他系统触发。
- 避免让池化对象自行决定归还到未知的全局池，从而隐藏所有权。
- 避免以单例作为所有对象池的默认作用域。
- 避免在归还后仍保留指向上一次使用者、目标、场景对象或事件源的引用。
- 避免为了减少创建次数而无限保留历史峰值容量。
- 避免只测试“能够再次显示”，却不测试行为、物理、异步任务和事件状态是否真正隔离。

## Common State Checklist

按对象实际使用的系统检查，不要求无关对象执行全部项目：

- Transform：父节点、局部/世界位置、旋转、缩放和激活状态。
- Rigidbody：速度、角速度、睡眠状态、运动学设置和约束。
- Collider：启用状态、接触相关状态和所属层。
- Animator：参数、当前状态、触发器和根运动影响。
- Particle/Trail：播放状态、存活粒子、拖尾和清除时机。
- Audio：播放、循环、时间位置和动态音量参数。
- Navigation：路径、目标、速度、停止状态和 Agent 有效性。
- Gameplay：生命值、阵营、目标、伤害来源、冷却和临时效果。
- Async：协程、任务、取消令牌、延迟回调、Tween 和订阅。
- References：上一次使用者、场景对象、资源句柄和外部注册。

## Exceptions

- 极少量对象可以不池化，即使它们理论上能够复用。
- 受第三方框架完整管理的对象可以遵循框架生命周期，但必须确认框架已经覆盖本规范关注的状态和资源风险。
- 在内存充足且性能尖峰比常驻内存更危险的平台，可以有意保留较大容量，但应记录平台依据。
- 原型阶段可以先不构建完整池化体系，但不应把临时实现直接视为生产规范。

## Validation

设计、实现或审查对象池后，检查：

- [ ] 有明确问题或测量依据支持池化决策。
- [ ] 已定义池的所有者、作用域和销毁时机。
- [ ] 已区分创建、获取、归还和最终销毁阶段。
- [ ] 每次获取都建立完整初始状态。
- [ ] 每次归还都停止异步行为并解除周期内订阅。
- [ ] 已处理重复归还、错误池归还和外部销毁。
- [ ] 已定义池为空、超过容量和获取失败的行为。
- [ ] 已验证场景卸载和跨场景引用。
- [ ] 已验证资源引用计数和最终释放时机。
- [ ] 已在代表性设备和真实负载下比较帧时间、GC 与内存。
- [ ] 已记录偏离 `MUST` 或 `SHOULD` 的原因和风险。

## Project Questions

以下信息会改变结论；需要时再获取：

- Unity 版本、目标平台和最低设备规格是什么？
- 对象的创建频率、峰值并发量和生命周期分布是什么？
- 当前性能问题是否已经通过 Profiler 或目标设备数据确认？
- 对象是否依赖 Addressables、场景对象、网络框架或第三方 Tween/特效系统？
- 项目是否已经定义统一生命周期接口、资源所有权或场景卸载流程？
- 更重要的约束是帧时间稳定性、加载时间、内存峰值还是实现复杂度？
