# 规范编写标准

## Purpose

让每项最佳实践可判断、可执行、可检查、可迭代，避免形成只表达偏好的知识文章。

## Required Structure

每份规范按需要使用以下章节；没有实际内容的章节可以省略：

1. `Purpose`：说明要控制的风险或改善的结果。
2. `Applies When`：列出适用条件。
3. `Does Not Apply When`：列出不适用条件。
4. `Decision Process`：提供需要判断时的最短决策流程。
5. `MUST`：记录违反后容易产生缺陷或重大维护风险的规则。
6. `SHOULD`：记录通常有益但允许合理偏离的规则。
7. `CONSIDER`：记录依赖规模、平台或测量结果的选择。
8. `AVOID`：记录默认不采用的反模式。
9. `Exceptions`：描述常见例外及其成立条件。
10. `Validation`：定义实现或审查完成后的检查清单。
11. `Project Questions`：列出缺少哪些项目信息会改变结论。

## Authoring Rules

- 使用指令性语言描述可观察行为，不写空泛口号。
- 每条 `MUST` 都要对应明确风险，并能够通过检查、测量或项目证据验证。
- 把依赖场景的建议写入 `SHOULD` 或 `CONSIDER`，不要滥用 `MUST`。
- 同时写明不适用条件，防止智能体机械套用规范。
- 优先描述目标、约束和验证标准；除非实现方式本身是规则，否则不要绑定具体库或 API。
- 不复制其他规范的内容；用直接链接表达关联。
- 若规则只适用于特定 Unity 版本、渲染管线、平台或包版本，必须在规则附近标明条件。
- 新增规范时，在 `SKILL.md` 中增加直接路由，并更新 `references/catalog.md`。

## Change Discipline

- 修正文案、歧义或错误示例时，保持规则含义不变。
- 新增 `SHOULD` 或 `CONSIDER` 时，确认不会悄然改变既有项目行为。
- 新增、删除或收紧 `MUST` 时，视为行为级变更；在发布说明中明确迁移影响。
- 废弃规则时，先标记替代方案和适用期限，再在后续主要版本中删除。
- 不在规范文件中维护重复版本历史；使用 Git 提交、Tag 和发布说明记录演进。

## Validation Cases

每项新规范至少准备以下三类真实任务进行验证：

- 正向任务：应触发并应用该规范。
- 反向任务：主题相近但不应机械采用该方案。
- 边界任务：信息不足或项目约束冲突，需要提问、保留判断或声明例外。

检查智能体是否读取了正确规范、区分了要求等级、使用了项目证据，并执行了最终检查清单。
