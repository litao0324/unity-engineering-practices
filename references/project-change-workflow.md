# 项目变更工作流

## Purpose

让 Unity 项目中的修改保持证据充分、范围可控、符合既有架构，通过与风险匹配的自测完成收口，并让用户知道受影响功能、实际验证结果和验收入口。

## Applies When

- 修改、重构或审查脚本、场景、Prefab、资源、配置或 Project Settings。
- 修复运行时错误、表现异常、构建失败、数据问题或性能回归。
- 一个任务会同时影响代码、资源和编辑器生成流程。

## Decision Process

1. 确认真正的 Unity 项目根目录和适用的项目规则。
2. 建立基线：记录分支、当前改动、问题现象和允许修改范围。
3. 沿实际入口、调用链、数据流和资源引用定位最小责任边界，列出受影响功能及验收场景。
4. 对照相邻实现和项目已有模式选择方案。
5. 只修改完成目标必需的内容。
6. 主动执行与风险匹配的静态、编译、导入、运行和回归验证，记录预期与实际结果。
7. 检查最终差异，只保留可追溯到当前目标的修改。
8. 交付功能变化、影响范围、自测证据、可操作的验收入口和未验证项。

## MUST

- 修改前必须读取适用的 `AGENTS.md`、项目说明和与任务直接相关的专项规范。
- 必须确认并保护工作区中已有的用户改动，不覆盖、回退或混入无法确认归属的内容。
- 必须区分第一方代码、第三方代码、生成文件和缓存/构建产物。
- 必须先寻找现有入口、同类实现、命名和架构边界，再引入新模式。
- 缺陷修复必须建立可观察症状与直接原因之间的证据链；不要因为堆栈停在公共框架就先修改框架。
- 变更必须限制在当前目标的最小范围；公共 API、序列化字段、Project Settings 和共享资源的修改要检查所有已知调用者。
- 修改前必须沿实际入口确认直接改变的功能和相关回归范围，为每项受影响功能定义进入方式、触发条件和预期结果。不得只用文件清单代替功能影响说明；尚未确认的影响必须标为待确认。
- 修改后必须主动执行当前条件下可运行且与风险匹配的自测，覆盖改变的行为、相关边界和关键回归路径。不得仅提供用户操作步骤而跳过能够自行完成的验证。
- 自测记录必须包含场景、操作、预期、实际结果及证据，逐项标记为已通过、失败或未执行；失败要区分已确认的基线问题、本次引入问题和归属待确认问题。证据可以是测试输出、Console 日志、已实际查看的运行截图或可复现的观察记录，不要求为每次改动另建报告文件。
- 涉及资源、Prefab 或 Scene 时，必须同时验证序列化引用与运行时表现；仅编译通过不算完成。
- 无法执行某项验证时，必须说明缺失条件、影响的验收结论和剩余步骤，并继续完成不依赖该条件的检查。未执行项不能写成通过；必要验证失败或未执行时，必须明确说明实现进度与验证缺口，不得宣称功能已完整验证或通过验收。
- 完成前必须检查工作区状态和差异，移除本次工作产生的临时绕过、调试内容和无关生成产物。
- 最终回复必须说明功能变化、影响范围、实际自测结果和用户验收入口；入口必须包含前置条件、具体操作及预期结果，且与已交付版本一致。未验证项必须单独标明，不能依赖被折叠的过程消息传达。

## Self-test Scope

按实际变化选择验证，不机械要求所有任务运行全部层级；更具体的专项规范仍须遵守。

| 变化类型 | 自测重点 |
| --- | --- |
| 玩法或业务逻辑 | 改变的正常流程、相关边界和相邻玩法回归；缺陷修复使用原触发条件验证，并与可获得的修改前症状对照 |
| UI、Prefab 或 Scene | 序列化引用、组件绑定、实际交互和重复进入退出；视觉变化按 [UI 与 Prefab 规范](ui-and-prefab.md) 提供并检查运行截图 |
| 动效或对象复用 | 连续触发、中途退出、结束清理和再次复用后的状态；按 [动效生命周期](animation-and-effects.md) 及 [对象池规范](object-pooling.md) 验证 |
| 存档或配置 | 实际读取入口、默认值、保存及重启恢复；改动影响兼容时验证已有数据 |
| 公共组件或共享资源 | 检查已知调用者，选择覆盖不同使用方式的代表性入口回归，并说明未覆盖范围 |
| 仅规则或说明文档 | 检查规则冲突、链接、触发范围和交付一致性；无运行时影响时不要求启动 Unity |

优先使用已有的 Unity Editor、EditMode/PlayMode 测试、已连接的编辑器工具或目标设备。对频繁回归且可稳定断言的逻辑，考虑增加自动化测试；低影响的文案、说明或简单配置调整采用针对性检查，不为形式新增测试框架。

## Delivery

最终回复按需要使用短段落或表格，覆盖以下内容；小改动可以合并表达，不强制固定长度或标题：

- 功能变化：玩家或使用者可感知的修改前后行为；内部重构说明预期行为是否保持及依据。
- 影响范围：直接入口和共享依赖影响的相关功能，区分已确认影响与待确认项。
- 自测结果：具体场景、已通过/失败/未执行状态及支持结论的证据；只有编译证据时只报告编译结果。
- 用户验收：前置条件 → 进入方式 → 操作 → 预期结果；优先给出真实功能入口，确需准备测试状态时说明现有准备方式，不猜测菜单或路径。
- 未验证项：缺失条件、可能影响和剩余验证步骤；没有时可以简写。

## SHOULD

- 应该把多步骤任务转成可验证的小目标，并为每一步提前定义验证方式。
- 应该优先使用针对性搜索和代表性文件，避开 `Library`、`Temp`、`Logs`、`obj`、构建输出和 IDE 缓存。
- 应该复用现有类、组件、服务和生成入口，避免为单次使用增加抽象或框架。
- 应该在任务开始时记录无法静态确认的内容，并在 Unity Editor、Play Mode 或目标设备中验证。
- 应该把不同目的的改动分开收口，保证每组差异可以独立解释和回滚。

## CONSIDER

- 当变更涉及多条入口、状态和资源时，考虑先建立简短的功能原型或调用链说明。
- 当公共组件必须修改时，考虑先通过局部适配验证方案，再决定是否扩大共享层改动。
- 当当前工作区过脏而无法可靠隔离修改时，考虑使用独立工作树或请求用户明确范围。

## AVOID

- 避免顺手重构、统一格式或清理与任务无关的历史问题。
- 避免从单个文件、类名或目录名推断完整架构。
- 避免通过新增 fallback、硬编码或修改底层加载器掩盖真实配置和引用问题。
- 避免把静态检查、项目文件编译或 Editor 模拟模式中的单一结果表述为完整验证。

## Validation

- [ ] 已确认项目根目录、项目版本和适用规则。
- [ ] 已记录并保护原有未提交改动。
- [ ] 修改范围中的每个文件都能对应用户目标。
- [ ] 已检查现有架构和相邻实现。
- [ ] 已列出受影响功能、真实入口、预期变化和相关回归场景。
- [ ] 已完成与风险匹配的静态、编译、导入、运行或设备验证。
- [ ] 每项自测都有操作、预期、实际结果、状态和可追溯证据。
- [ ] 已检查公共调用者、资源引用和关键回归路径。
- [ ] 最终差异不包含临时绕过和无关生成产物。
- [ ] 无法验证的内容、假设和残余风险已明确说明。
- [ ] 最终回复包含功能变化、影响范围、自测结果及可执行的用户验收步骤，结论没有超出证据。

## Validation Cases

- 正向：修改共享 UI 交互或玩法逻辑，应沿真实入口列出受影响功能，执行正常流程、相关边界及代表性调用者回归，交付实际结果和用户验收步骤。
- 反向：仅修正规范文档链接，无运行时影响，应验证引用及规则一致性并说明适用流程，不要求启动 Unity 或新增玩法测试。
- 边界：实现已修改但编辑器连接或设备条件缺失，应完成可执行的静态检查，明确运行项未执行、所缺条件及验收步骤，不得把编译或静态结果扩写为功能通过。

## Project Questions

- 真正的 Unity 根目录、目标分支和允许修改范围是什么？
- 当前工作区有哪些已有改动，分别属于谁？
- 项目规定的编译、测试、资源生成和运行验证入口是什么？
- 哪些目录属于第三方、生成内容或禁止修改区域？
- 本次变更最重要的用户可感知验收结果是什么？
- 用户从哪个入口、在什么状态下能观察到改动？哪些共享调用者需要回归？
- 当前有哪些可执行的自测工具和测试状态准备入口？哪些验证必须在目标设备上完成？
