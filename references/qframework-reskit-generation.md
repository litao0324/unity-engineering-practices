# QFramework ResKit / QAssets 生成

## Purpose

保持资源标记、生成的资源名常量与实际加载链路一致，避免新增资源只有编辑器可见、运行时却无法加载。

## Applies When

- 项目已经使用 QFramework ResKit、`QAssets.cs` 和 `QAssetBundle` 常量。
- 新增、导入、移动、重命名、删除或引用需要 ResKit 加载的 UI、美术、Prefab 等资源。
- 排查常量缺失、AssetBundle 标记或对象池资源加载问题。

这是框架专项流程，不要求使用 Addressables、Resources 或其他加载架构的项目改用 ResKit。项目资源目录、生成文件路径、Bundle 命名和加载封装由使用方文档指定。同时执行 [资源与生成文件规范](assets-and-generated-files.md)。

## Workflow

1. 查目标项目的资源目录、相邻资源 `.meta`、`QAssets.cs`、生成器实现及 ResKit 配置，确认当前版本的输入、输出和实际运行加载模式。
2. 将资源放入项目指定目录，保留正确 `.meta`；按项目约定设置 AssetBundle 标记。支持此菜单的版本可使用 `Assets/@ResKit - AssetBundle Mark`，不凭示例猜测 Bundle 名。
3. 在 Unity 中执行已确认的资源名常量生成入口。常见入口是 `QFramework/Res Kit` → `生成代码（资源名常量）`；仅在目标版本确实存在相应方法时，才使用 `QFramework.BuildScript.WriteClass` 等批处理入口。
4. 检查生成结果包含实际资源对应的 `QAssetBundle` 类、资源常量和所需 Bundle 标识，核对重命名/删除后是否存在失效调用。生成成功不要求文件必然出现 diff，已有正确常量时无变化是合法结果。
5. 通过项目现有加载封装引用生成常量；对象池初始化同样使用常量，不另外创建硬编码加载路径。
6. 检查 diff、Unity 编译、资源导入及实际加载。生成常量不等于打包资源；需要构建/运行时 Bundle 的任务，还要按项目入口构建并验证对应模式。

## MUST

- 采用本链路的 ResKit 调用必须使用生成的资源标识，不因常量暂缺而硬编码 Bundle 名或资源名绕过。
- 普通资源工作不得手改 `QAssets.cs`，也不得为了绕过生成去修改 QFramework 源码。生成器缺陷应在明确的生成器修复范围内处理。
- 必须保持资源与 `.meta`、GUID、标记及引用同步，不随意重命名或重新分包已有资源。
- 菜单、Unity 或生成器不可用时，说明已完成内容、缺失常量和待执行入口；不伪造生成成功，不手写“临时常量”掩盖阻塞。
- 同一工程已有 Unity Editor 打开时，不启动第二个进程强占工程；优先用已连接的 Editor 执行，必要时请用户协调关闭，不擅自终止进程。
- 生成出现无关改动时检查来源；保留用户原有改动，只处理本次造成且确认无关的内容。

## Validation

- [ ] 资源目录、Bundle 标记、生成入口及输出路径来自当前项目证据。
- [ ] 所需常量存在且值与实际资源一致；新增调用没有裸资源名绕过。
- [ ] 资源及 `.meta` 完整，移动/删除后的引用已检查。
- [ ] 生成 diff 可解释；没有手改生成结果或无关框架代码。
- [ ] Unity 编译、导入及任务要求的加载模式已验证；未执行项已明确记录。

## Validation Cases

- 正向：导入新 UI Prefab 并注册对象池，按标记→生成→常量引用→实际加载验证闭环完成。
- 反向：仅修改游戏算法，没有资源或标记变化，不机械重生成 QAssets；使用其他资源系统的项目也不迁换框架。
- 边界：菜单不可用或常量生成后没有 diff，分别检查工具可用性和常量正确性；前者保留待生成状态，后者不能仅凭无 diff 判定失败。
