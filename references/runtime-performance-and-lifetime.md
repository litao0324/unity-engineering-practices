# 运行时性能与生命周期规范

## Purpose

让运行时 CPU、GC 和资源占用可预期，避免高频查找、无谓分配、资源泄漏和失去所有者的异步工作。具体成本随 Unity 版本、后端、平台和包变化，不以 API 名称代替项目测量。

## Applies When

- 新增、修改、重构或审查运行时 C# 逻辑，包括由运行时调用的工具方法。
- 排查逐帧、输入、动画、渲染、高频循环或路径构建中的性能回归。
- 管理事件、任务、协程、运行时 Mesh、Material 或其他有释放责任的资源。

## Does Not Apply When

- 一次性离线处理、低频 Editor 工具不自动适用热路径禁用规则；仍检查其资源所有权和真实耗时。
- 加载、初始化、存档恢复等允许有边界的分配和查找；若会造成可感知尖峰，仍需按真实调用频率评估。
- 不要求历史代码全量优化，不要求每次修改都达到零 GC 或引入对象池。

## Decision Process

1. 沿入口与调用链识别频率、循环规模、并发量和运行阶段；不能仅凭方法是否叫 Update 判断。
2. 确认目标设备、性能预算和现有证据；缺少测量时标记风险或假设，不声称优化收益已确认。
3. 优先显式依赖、初始化缓存、复用缓冲区和移出高频路径，再按问题选择专项方案。
4. 明确事件、任务和资源的所有者、有效周期、退出条件及释放位置。
5. 做与风险匹配的静态和运行验证；涉及热点变化时检查代表性负载下的帧时间、分配和内存。

## MUST

### Hot Paths

热路径包括 `Update`、`LateUpdate`、`FixedUpdate`、高频手势/动画/渲染回调、紧密循环、路径构建循环及其调用链。并非所有回调或循环天然高频，应按实际次数与规模确认。

- 高频使用的依赖必须在初始化或依赖建立阶段缓存；依赖会更换或失效时，同时定义刷新和清理策略，不能永久使用失效缓存。
- 在热路径中，未经本规范 Exceptions 的证据和评审，不得引入下表模式。审查新代码时发现这些模式应先调整方案，而不是仅增加风险备注。

| 模式 | 默认处理方式 |
| --- | --- |
| `FindObjectOfType`、`FindAnyObjectByType`、`GameObject.Find`、`transform.Find` | 序列化引用、初始化传参或初始化查找后缓存；只使用项目 Unity 版本支持的 API |
| 重复、未缓存的 `GetComponent`、`GetComponentsInChildren`、`GetComponentInParent`、`Camera.main` | 缓存实际目标，处理动态组件、相机或层级变化；不以某版本的内部优化替代依赖管理 |
| LINQ、反射 | 移到低频阶段，或使用明确循环、缓存的元数据/访问方式；检查实际枚举和分配 |
| 每帧创建引用对象、临时集合/数组、数组复制、捕获闭包、装箱 | 复用有明确所有权的缓冲区，或调整数据流；按实际分配检查，不把所有 `new` 或值类型构造都视为托管堆分配 |
| 日志字符串拼接/插值、高频日志 | 在构造字符串之前判断条件；按下方日志要求处理 |
| 重复 `Instantiate` / `Destroy` | 先检查创建频率和尖峰，再按 [对象池规范](object-pooling.md) 判断，不要求所有对象池化 |

### Logs

- 生产热路径不得保留无节制的 `Debug.Log` 或同类日志；必要诊断必须有明确目的和频率边界。
- 高开销调试日志必须在编辑器条件编译或调试开关后执行，确保关闭时不继续构造昂贵字符串或计算日志参数；仅依赖日志函数内部丢弃输出不够。

### Events And Async

- 事件订阅必须有对应的退订或由框架证明的等价生命周期管理；注册和清理与实际有效周期匹配，防止重复注册和悬挂引用。
- 异步、协程、延迟回调和 fire-and-forget 工作必须有明确所有者、异常观察及终止或失效机制；从逐帧或高频输入触发时必须限制并发，不能无限启动。
- 对象禁用、销毁、回池、退出会话或场景切换等出口必须按任务的实际作用域处理取消、停止或结果失效。应用级任务可以跨面板禁用继续运行，但不能回写已失效对象；无法取消的外部调用仍须观察错误并隔离过期结果。
- 不得假定所有协程、Task 或第三方库在 `OnDisable` / `OnDestroy` 的行为相同；核对当前框架的清理语义。动效和池化对象的额外检查分别见 [动效生命周期](animation-and-effects.md) 与 [对象池规范](object-pooling.md)。

### Runtime Resources

- 创建、重复生成或替换运行时 Mesh、Material 等资源前，必须明确实例所有者、共享边界、旧实例释放与最终释放时机；不能只覆盖引用而遗漏清理。
- 必须区分共享资源和当前功能创建的实例，不得销毁不属于自己的共享资源；带句柄或引用计数的资源使用项目既有释放协议，不能统一调用 Destroy。
- 可能隐式生成材质实例的访问必须核对实际需求与所有权，避免无意增加实例数量；不因减少实例而破坏设计需要的独立材质参数。

## SHOULD

- 高频逻辑应该复用 `List`、数组、StringBuilder 和临时缓冲区，结合并发与重入边界设计所有权；按已知规模设置容量，不为追求零扩容无限预留内存。
- 应检查闭包捕获、枚举器、装箱和集合 API 的实际分配；不把所有 foreach、委托或枚举都一律改写。
- 高频重复的 yield 指令仅在等待参数、可变状态与并发语义允许时缓存；不能跨协程共享承载可变等待状态的实例，也不能为缓存改变等待时长或时间尺度。
- 日志应低频、有目的、便于定位；仅为性能规范修改时不顺带删除必要错误诊断。
- 检查事件、任务或内存问题时，应验证重复启停、退出、切关及长时间运行的稳定性。

## Exceptions

热路径表中的例外仅在以下条件同时满足时成立；不适用高频限制的初始化和离线工具不需要伪造例外：

1. 标准缓存或复用方案在当前场景明显更差，或与已确认的平台/框架约束冲突。
2. 变更或评审记录说明调用频率、规模、CPU/分配/内存代价及采用原因，维护者能够理解影响；涉及性能收益的结论有对应测量，缺少测量不能宣称已验证。
3. 例外范围和评审结论明确，符合项目性能预算与更高优先级约束；不能仅用代码注释自行豁免项目禁令。需要用户明确要求的项目仍遵守其要求，不增加全库统一的审批步骤。

事件、异步和资源所有权的 MUST 不因性能例外被豁免；覆盖规则遵循 [Skill 优先级](../SKILL.md#precedence)。

## Validation

- [ ] 已确认热路径入口、调用链、频率、规模和目标平台。
- [ ] 查找与组件依赖已缓存或有成立的例外，动态依赖的缓存会正确刷新。
- [ ] 已检查 LINQ、反射、字符串、临时对象、闭包、枚举和装箱的实际分配风险。
- [ ] 调试日志关闭时不产生昂贵参数，高频生产日志有界。
- [ ] 事件成对管理，任务有所有者、并发边界、异常观察和退出策略。
- [ ] Mesh、Material 及资源句柄有明确的共享/实例归属及释放协议。
- [ ] 重复启停、取消、退出与必要的复用场景已按影响范围验证。
- [ ] 热点变化已按条件检查帧时间、GC 和内存；未执行的设备测量与性能结论明确区分。
- [ ] 有意偏离已记录原因、代价和评审结论，专项规范检查没有遗漏。

## Validation Cases

- 正向：拖拽回调每次查询相机、创建临时 List 并启动任务，应缓存依赖、复用缓冲、限制并发，验证拖拽、退出和再次进入。
- 反向：关卡恢复只调用一次的 DTO 转换创建结果集合，或离线导出工具使用 LINQ，不要求零分配，不为了表面合规引入全局共享缓存或对象池。
- 边界：依赖运行时更换，或异步由应用级服务拥有，分别设置缓存刷新和正确作用域；无目标设备数据时完成静态检查并保留测量缺口，不宣布性能达标。

## Project Questions

- Unity 版本、脚本后端、目标平台、代表性设备与性能预算是什么？
- 实际调用频率、集合规模、并发量和已有 Profiler 证据是什么？
- 谁管理事件、异步任务、相机切换、对象池和资源释放？
- 项目是否有比本库更严格的热路径限制、日志策略或例外评审要求？
