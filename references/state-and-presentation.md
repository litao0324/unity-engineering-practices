# 业务状态与表现隔离

## Purpose

避免临时动画、外观随机和可变资源顺序改变业务状态、输入容量或恢复结果。动效清理见 [动效生命周期](animation-and-effects.md)，测试隔离见 [测试数据与运行夹具](test-data-and-fixtures.md)。

## Applies When

- 可并发的业务操作与异步动画分别维护逻辑对象、视觉对象和待清理对象。
- 随机外观需要在刷新、撤销或续关中保持，或与玩法随机共存。
- 保存对象/资源选择，处理目录顺序、候选列表或资源更新后的旧存档。

不要求所有玩法允许并发，不要求纯临时装饰持久化，也不强制改用某种存储库或随机算法。

## MUST

- 涉及逻辑与表现双列表时，必须明确业务状态的权威来源及每个集合的职责；容量、匹配和可操作条件依据已确认业务规则，不以尚未结束的视觉对象数量额外限制本来允许的操作。
- 保留业务要求的事务边界、专用输入锁和单对象防重复；不能为了连续操作移除必要锁，也不能为了等待动画新增无依据的全局锁。
- 外观随机若要求不影响玩法结果，必须与玩法随机状态隔离，并验证随机调用不会改变后续业务结果；不要求重写本身已隔离的机制。
- 需求要求跨刷新、撤销或续关一致的随机结果必须保存并恢复；新局抽取与快照恢复分别定义，不在恢复时无依据地重新抽取或按新筛选规则改写旧局。
- 持久化选择必须使用稳定身份或版本化映射，不能让候选数组排序、资源增加或删除静默改变旧选择的含义。缺失资源按已确认规则回退，不默认按新索引映射到其他资源。

具体存储的 Key、类型兼容、缓存同步和原子性继续遵循项目实际实现；采用生成式 ES3 链路时读取 [对应专项规范](statusutil-es3-persistence.md)。

## Validation

- [ ] 快速连续操作、重复操作及必要的锁定路径符合业务规则，视觉滞留不产生额外容量限制。
- [ ] 随机表现没有改变需保持的业务输入或随机状态。
- [ ] 要求一致的刷新、撤销、续关结果已验证，旧存档与缺失资源回退符合约定。
- [ ] 调整候选顺序/数量后，已保存的稳定身份仍解析为原选择。

## Validation Cases

- 正向：已配对对象仍在消失，业务容量已释放；验证后续合法输入，同时保留单对象防重复和专用锁。
- 反向：回合制或权威流程必须等待确认，保留其串行规则；只出现一次且不需恢复的随机装饰不新增存档。
- 边界：旧存档保存列表索引或所选资源已删除，先确认版本映射与回退策略，不随意重抽或强制迁移全部存档。
