# StatusConfig / StatusUtil / ES3 状态持久化

## Purpose

复用项目已有状态生成链路，让默认值、存档 Key、生成属性、缓存读写和同步策略保持一致。

## Applies When

- 项目已经使用 `StatusConfig` 定义默认值、生成 `StatusUtil.auto.cs`，并通过 ES3 Cache 持久化。
- 新增、修改、审查或使用玩家/游戏状态字段，处理默认值、旧存档或保存频率。

这不是要求所有 Unity 项目安装 ES3 或改用 StatusUtil。源码路径、生成器、菜单及业务例外由项目文档提供；先确认当前实现。生成文件规则同时见 [资源与生成文件规范](assets-and-generated-files.md)。

## Workflow

1. 搜索现有 `StatusConfig`、`StatusUtil`、生成结果和业务调用，确认是否已有字段，避免重复 Key 或第二套存储。
2. 阅读当前生成器、默认值及缓存初始化/同步逻辑。确认字段名到 Key 的映射、支持的类型、生成声明格式及是否已有手写 partial 扩展。
3. 在生成源中增加或修改字段。采用逐行正则解析的生成器时，沿用其支持的单行、显式类型、`public static` 声明和默认值格式；不要未经验证改用多行初始化、属性或推断类型。
4. 执行目标项目的状态生成入口。沿用 Mola 工具链的项目常见菜单为 `MolaUtil/自动化/生成StatusUtil`，实际以目标项目实现为准。
5. 检查生成属性的类型、默认值、Key 和读写逻辑。常见契约为 getter 从 Cache.Load 读取并以 StatusConfig 兜底，setter 经 Cache.Save 后 Cache.Sync；不可假定其他版本完全相同。
6. 业务代码使用 `StatusUtil.FieldName` 等已确认的公共入口；验证新存档默认值、已有值、写入后重载和业务重进，再检查生成 diff。

## MUST

- 默认值和新增字段必须维护在生成源，普通业务任务不手改 `StatusUtil.auto.cs`，不因工具不可用而手补生成属性。
- 不把 `StatusConfig` 当运行时存储；不无故引入 PlayerPrefs、新存储文件或第二套持久化系统。
- 字段名作为存档 Key 时，重命名、删字段、改类型必须评估旧存档兼容及迁移。修改默认值只影响缺省读取，不能宣称已覆盖玩家已有值。
- 集合或对象通过 getter 取出后原地修改，不代表已经持久化；必须按当前缓存实现执行明确的保存/同步，并验证重载结果。
- 对可变默认对象要检查共享引用和意外修改风险，不能让一次业务写入悄悄改掉后续缺省值。
- 工具不可用时可完成安全的生成源准备，但必须说明待生成/待验证项；不得继续把不存在的生成属性当作可编译成果。
- 不在普通加字段任务中顺手重写生成器、缓存机制或无关存档。

## Existing Batch-Save Extensions

如果项目已有经确认的手写 `StatusUtil` partial 批量保存入口，可沿用同一 ES3 Cache、相同 Key 及已建立的 Sync 时机，避免多字段逐项立即 Sync。需确认没有 Key 分叉、遗漏同步、缓存未初始化或失败后数据不一致；涉及可变集合时同样验证重载。

这类入口是项目明确的扩展，不是允许把生成字段随意移到手写文件。一次 Sync 也不自动等于具备事务原子性；原子性需求必须另查存储实现并验证失败恢复。迁移既有手写字段或改变同步策略属于额外变更，先说明影响。

## Validation

- [ ] 已复用现有字段/Key，新增声明被当前生成器正确识别。
- [ ] 已生成对应属性，类型、默认值、Key、Save/Sync 行为正确，未手改生成结果。
- [ ] 新存档、旧存档、缺失 Key、读写重载及必要的迁移已验证。
- [ ] 集合修改、批量保存及缓存初始化遵循已确认的项目契约。
- [ ] Unity 编译/Console 和业务重进验证已执行，测试使用隔离或可恢复存档；未执行项已说明。

## Validation Cases

- 正向：新增领取标记，先在 StatusConfig 声明默认值，再生成属性，通过 StatusUtil 写入并验证重载。
- 反向：只需一局内的临时 UI 状态，不强行持久化；其他存储架构不替换成 ES3。
- 边界：旧 Key 改名、集合原地修改或已有批量保存扩展时，先确认兼容与同步，不用“编译通过”代替保存验证；没有 Unity 时不手写生成属性。
