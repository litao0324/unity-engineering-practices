# 测试数据与运行夹具

## Purpose

让测试覆盖实际使用的数据和初始化路径，同时保护正式资源、存档及编辑器状态。自测证据与交付方式见 [项目变更工作流](project-change-workflow.md)。

## Applies When

- 为复现、验证玩法或界面准备临时数据、快照、运行实例或组件夹具。
- 同一功能可能读取内置资源、在线缓存、活动资源或已有存档。
- 在隔离环境直接调用真实组件，或验证新局、重开和续关。

不要求无状态纯函数测试启动完整游戏；项目已有正式测试框架、依赖注入和固定测试资产时沿用其入口。临时注入与长期测试设施分别管理，不能一概删除正式测试。

## Workflow

1. 记录复现入口、实际数据来源和版本/索引、运行类型、初始化前置条件及是否恢复快照；同名资源不代表同一内容。
2. 选择覆盖目标路径的最小准备方式：优先既有读取器、转换器和测试入口；需要修改运行数据时，确认所有相关入口经过该位置，且后续初始化不会覆盖修改。
3. 列出会改变的状态，使用隔离实例/测试存档，或备份可恢复状态。清除进度、新开关卡和触发业务按钮可能写入存档，不当作只读操作。
4. 经真实入口验证；无法运行完整链路时，可调用真实组件做隔离检查，但明确其不覆盖分发、触发条件和完整玩法。
5. 清理本次临时内容并恢复状态，再检查正式读取及恢复路径没有变化；保留项目规定的长期测试设施。

## MUST

- 必须确认实际读取来源；在线缓存、远端资源与内置回退分别记录，不能用目录名或泛型名称推断正在运行的玩法。
- 不为复现测试改写正式生产资源；存档操作使用隔离状态或可恢复备份，不能永久改变玩家进度。用户明确要求修改正式数据的任务按其授权范围另行处理。
- 临时运行数据修改必须集中、可定位，并保持正式解析/转换、类型分发和初始化顺序；数据有效性、坐标及对象身份来自实际运行数据。
- 目标涉及续关时，必须单独检查快照恢复路径。新局转换器中的注入不能证明旧快照也已覆盖；不能为了测试方便改变正式恢复逻辑。
- 临时单例引用、随机状态、场景/实例和测试存档的改动必须有对称恢复；只恢复本次改变的状态，不覆盖用户原有编辑器改动。
- 必须清理临时注入及专用辅助内容，按实际风险验证清理后的正式入口；测试夹具通过不能表述为完整功能验收。

## Validation

- [ ] 已记录实际来源、版本、入口、类型、初始化条件及新局/快照状态。
- [ ] 临时修改在目标链路生效，未被后续转换覆盖，也未绕开正式分发。
- [ ] 实际可执行的组件或功能检查已完成，结论限定在覆盖范围内。
- [ ] 测试状态已恢复，正式数据、生产配置和原有用户改动得到保护。
- [ ] 临时内容已清理；需要的新局及恢复路径回归已执行或明确未执行。

## Validation Cases

- 正向：缓存关卡与内置同名文件不同，先确认运行来源，再在覆盖相关入口的转换边界准备可恢复数据并验证。
- 反向：无状态算法或已有隔离测试资产直接测试，不强制注入生产转换器，也不禁止项目原有测试开关。
- 边界：旧快照绕开新局转换或初始化未完成，分别准备对应状态；只有组件验证条件时报告组件结果，保留真实入口待验证项。
