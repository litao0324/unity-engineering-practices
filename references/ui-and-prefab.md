# UI 与 Prefab 规范

## Purpose

让 UI 结构在 Prefab 中可见、绑定稳定、组件可复用、生命周期完整，并在不同文案、分辨率和重复打开场景下保持正确。有明确效果图的实现必须 100% 还原设计，不能出现位置、大小、间距或适配偏差。

## Applies When

- 新增或修改面板、弹窗、按钮、文本、图标、列表、布局和 UI 动效节点。
- 修改 Prefab 层级、序列化字段、自动生成绑定或面板初始化顺序。
- 修复 UI 丢引用、重复事件、错位、无法点击或重复打开状态异常。
- 按效果图新增、调整、迁移或验收 UI，包括局部气泡、底板、图标和数量文字。

## Visual Acceptance Scope

- 下文的效果图复刻规则适用于本次任务明确要求实现的最终效果图及目标区域；风格灵感图、无效果图的逻辑修复或明确不在本次范围内的界面，不自动变成重做整个 UI 的任务。
- 没有效果图时沿用已确认的项目视觉规范；迁移任务按 [功能迁移规范](feature-migration.md) 建立源运行画面基线，不把猜测或任意模板当成设计。
- 规则适用于不同 UI 架构。uGUI 检查 Prefab、RectTransform 和 CanvasScaler；UI Toolkit 检查 UXML/USS、最终布局和 PanelSettings；其他系统检查其对应的布局、缩放与生命周期，不强行改成 Prefab 实现。
- 连续迭代必须保留已确认的验收基准、任务范围及未完成项，只有用户明确变更要求时才更新。局部修正不自动取消其他有效要求；验收结论必须限定在证据实际覆盖的范围内。

## Decision Process

1. 同时检查目标 Prefab、手写逻辑、生成绑定和相邻同类界面。
2. 确认最终效果图、原始尺寸、界面状态和适配规则，再检查项目已有的基础面板、文本、按钮、列表和样式配置。
3. 区分稳定结构与运行时数量确实可变的内容。
4. 在 Prefab 或配置的正确层级完成结构修改，再通过项目生成流程更新绑定。
5. 验证初始化、交互、关闭、重开、分辨率和多语言，并按效果图完成运行截图对照。

## MUST

- 必须保持 Prefab 节点、序列化字段、生成绑定和手写逻辑双向一致。
- 稳定存在的 UI 节点和组件必须在 Prefab 或项目规定的模板中创建，不要在运行时临时补齐结构。
- 项目使用绑定生成器时，必须通过生成源和生成器更新字段，不直接长期修改生成文件。
- 必须明确点击事件、数据订阅、Tween 和异步回调的注册与清理时机，防止重复打开后累积。
- 面向玩家的文本必须遵循项目本地化流程，并验证占位符和文本长度变化。
- 修改 Prefab 时必须保留 `.meta` 和现有序列化引用；新增资源要确认运行时可加载。
- 视觉禁用与实际不可交互必须分别验证，不能只根据颜色或置灰状态推断交互已经关闭。

### 图片资源与颜色组合

- 使用 uGUI `Image` 显示 Sprite 时，必须同时核对素材原色、组件 `color` 的 RGB/Alpha、材质及驱动颜色的配置或逻辑，判断组合后的最终颜色是否符合有效设计或源运行基线。Sprite 引用正确不能证明显示颜色正确；其他 UI 系统按其对应的图片着色机制检查。
- 需要保持彩色素材原色且没有设计染色时，组件 RGB 应为白色，Alpha 按设计保留；白色图标着色、置灰、主题切换及颜色动画等有意染色必须保留并验证，不能批量把所有图片设为白色或不透明。
- 迁移或复用组件时，必须检查颜色枚举的语义、初始化/样式刷新、数据刷新及相关动画赋色，并核对基础 Prefab、Variant 和各层嵌套覆盖后的有效颜色。关闭自动颜色配置不会自动恢复已写入的错误颜色；必须依据基线修正实际色值及导致偏色的覆盖，不能只清空枚举或只修基础 Prefab。
- 必须验证保存并重新加载后的新实例，在初始化、相关刷新、关闭重开及适用动画状态下检查实际颜色并审查运行截图；存在默认隐藏图片时要触发其显示状态。不得只检查资源 GUID、资源文本中显式声明的组件或编辑器预览。

### 效果图 100% 复刻

- 必须以需求方最终确认的效果图为视觉验收基准，做到 100% 一模一样；位置、大小、比例、间距、内边距、层级遮挡、颜色、字体、描边、阴影及装饰细节均不得有偏差。不得自行设置像素误差或相似度容差，也不能以“看起来接近”通过验收。
- 修改前必须记录原图文件/版本、原始像素尺寸、视口、安全区、界面状态、语言和展示数据，逐项量取目标区域及子元素的可见边界、中心位置、宽高、间距和对齐关系。不能以缩略图量尺寸，也不能遗漏底板、数量文字、尖角或隐藏状态下才出现的元素。
- 必须核对准确素材、字体及其最终渲染边界，包括透明留白、裁切、九宫格、像素密度、父级缩放和字形度量；不得以近似素材、替代字体、随意染色或非等比拉伸掩盖差异。本地布局数值相同不代表屏幕显示相同。
- 复用组件、默认模板、源项目旧界面和目标项目样式不能覆盖已确认的效果图。必须在正确的资源、规格或局部布局层实现设计，只有需求方明确修改设计后才能更新验收基线。
- 必须检查保存值与运行时初始化、资源/字体加载、布局重建、数据刷新、样式继承和嵌套覆盖后的最终显示，防止运行逻辑重新写入错误的位置、尺寸或样式。
- 必须按目标元素的完整视觉构成及适用状态核对最终渲染，包括资源、布局、颜色、文字和附加效果。既有、继承或迁入配置同样需要验证。局部修改必须复核目标元素的整体结果，并保留任务范围内其他已知差异的验收状态。

### 适配与运行截图验收

- 效果图对应分辨率必须逐像素对齐；其他受支持分辨率必须遵守已确认的适配图或项目适配规则，保持规定的尺寸/缩放关系、间距、对齐和安全边界，不得错位、变形、重叠、裁切或越界。
- 必须记录并验证本次支持范围的适配矩阵，至少覆盖设计基准分辨率、最窄/最宽宽高比，以及范围内的安全区和广告等占位状态；支持平板或横竖屏切换时一并验证。检查实际 UI 系统的参考分辨率、缩放策略、父级布局与安全区处理，不从单张效果图猜测所有设备的排布。
- 必须通过真实入口打开保存并重新加载的界面，在资源、字体、布局和数据稳定后获取运行截图；不能以编辑器预览或未保存的运行时手工调整代替验收。首次打开、关闭重开、数据刷新和分辨率变化后的布局都要检查。
- 必须在与效果图相同的分辨率、状态、语言、展示数据及渲染条件下进行原尺寸并排、叠加或差分对照，检查完整目标区域及其在整屏中的位置。动画按相同状态/时间点比较，局部放大只能辅助整体验收。
- 对照只能按记录的视口坐标统一对齐，不得单独平移、缩放或拉伸元素，也不得裁切、遮盖差异来制造一致。必须逐项消除差异，不能只凭总相似度或少数边界尺寸判定通过。
- 需要复现设计中的展示数据时，必须使用隔离、可恢复的测试状态，再验证真实动态数据、长文案和不同元素数量；不得为了截图一致修改正式业务配置、规则或玩家真实存档。
- 必须记录效果图版本、运行截图路径、验证分辨率/状态和对照结果。任一视觉或适配差异未消除，均不得通过对应验收或宣称“已完成/100% 复刻”。缺少原图、准确资源、适配规则或运行条件时，明确缺口并补充/确认，保留未验证项；可继续不受影响的工作，但静态检查和编译通过不能替代视觉验收。
- 交付前必须实际审查最终运行截图，并逐项对照验收基准。任务范围内的可见差异必须修复或标记对应验收未通过；证据、验收记录与完成说明必须一致。生成截图及静态配置检查均不能替代对最终画面的审查。

## SHOULD

- 应该优先复用项目已有的基础组件、样式配置和同类 Prefab，避免复制近似组件。
- 应该只绑定脚本确实需要访问的节点；纯装饰和固定结构留在 Prefab 中。
- 应该通过直接绑定字段访问稳定节点，避免按名称搜索层级。
- 应该让同类界面沿用既有命名、层级、锚点、安全区和打开/关闭流程。
- 应该在结构修改后重新打开 Prefab，检查默认隐藏节点、嵌套 Prefab、Missing Script 和必填引用。
- 应该验证首次打开、重复打开、快速点击、中途关闭和数据刷新。

## CONSIDER

- 数量很大或持续变化的列表考虑虚拟化；少量固定节点优先保留在 Prefab。
- 设计出现可稳定复用的新规格时考虑提升到共享配置；一次性偏移或局部动画留在具体 Prefab。
- 动态创建确有数量变化、延迟加载或复用需求时可以采用，但要明确创建、绑定、回收和失败路径。

## AVOID

- 避免使用全局名称查找或深层遍历获取稳定 UI 节点。
- 避免在业务脚本中动态添加本应由 Prefab 配置的组件。
- 避免直接覆盖已有同名 Prefab，先比较节点、Override、绑定和业务差异。
- 避免为了视觉统一移动或重构与当前需求无关的特殊界面结构。
- 避免把运行时显示正常作为唯一验收；隐藏节点、其他分辨率和下一次打开也可能失败。

## Exceptions

- 第三方控件、程序化 UI 或数据驱动渲染可以动态构建结构，但必须遵循该系统自己的生命周期与测试方式。
- 对自包含的动态子树进行局部组件查询可以接受，不应扩展成跨面板的名称查找惯例。

## Validation

- [ ] 已检查 Prefab、手写逻辑、生成绑定和相邻用法。
- [ ] 有效果图的任务已记录原图版本、分辨率、状态和布局测量基线，没有用默认模板替代设计。
- [ ] 连续迭代沿用已确认的设计与未完成项，单项验证结果没有被扩大为整页或原任务的验收结论。
- [ ] 已核对目标元素的完整视觉构成及适用状态，包括既有、继承或迁入配置的最终结果。
- [ ] 图片素材原色与组件 RGB/Alpha、材质、颜色配置及嵌套覆盖组合正确，新实例初始化和相关刷新后无意外染色，有意染色及透明度仍符合设计。
- [ ] 已复用项目组件和样式，或记录新增规格的理由。
- [ ] 没有直接维护本应生成的绑定文件。
- [ ] 节点、字段、脚本和资源引用完整。
- [ ] 点击事件不会重复注册，关闭时会清理周期内状态。
- [ ] 本地化、长文本、占位符和必要的 RTL 表现正确。
- [ ] 已检查目标分辨率、安全区、层级和遮挡。
- [ ] 首次、重复、快速操作和中途关闭行为正确。
- [ ] 已对保存并重新加载后的运行画面完成原尺寸对照，位置、大小、间距及视觉细节无偏差，截图证据已记录。
- [ ] 已验证受支持分辨率、安全区、占位状态和动态内容的适配矩阵，没有用单一分辨率代替适配验收。
- [ ] 未消除差异和未验证项已明确标为未通过验收；没有以静态检查或“近似一致”宣称完成。
- [ ] 已查看实际交付的最终截图；截图中的可见差异与验收记录、对用户的完成说明一致。

## Applicability Checks

- 彩色图片需要保持原色，却被组件颜色或上层覆盖二次染色时，定位并修正错误赋色来源，再验证新实例与重开后的画面。
- 白色图片有意通过颜色配置着色，或设计要求半透明、置灰和颜色动画时，保留对应效果并验证状态，不机械清空颜色配置或统一设为白色。
- 无法确认图片是否应染色或源运行基线不可用时，记录资源与各层有效色值，保留待验证项，不凭素材颜色猜测并批量修改。
- 有明确视觉基准及目标区域时，执行完整视觉与适配验收；局部修改保留有效基准并复核受影响元素。
- 没有视觉变更要求的逻辑修复，验证行为及原有布局无回归，不自动扩大为视觉重做。
- 缺少资源、设计或运行条件时，继续可确定的工作，明确未验证项并保留其未通过状态。
- 用户明确限定或变更范围时，按最新范围执行及报告；未被变更的要求继续有效。
- 不同 UI 架构使用各自的结构、样式和生命周期机制，均以最终渲染结果及同一有效基准验收。

## Project Questions

- 项目使用哪套 UI 框架、绑定生成器和基础组件？
- UI 结构由 Prefab、UI Toolkit、代码还是混合方式管理？
- 设计分辨率、安全区和最低支持宽高比是什么？
- 最终效果图的版本、原始尺寸、界面状态和数据是什么？支持范围内其他宽高比的适配规则是否已确认？
- 面板生命周期和事件清理由谁负责？
